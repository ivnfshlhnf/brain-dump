# Audit — brain-dump (ui-design-06-audit-pass)

A code-level technical quality audit of the implementation as it stands after the
harden → bolder → optimize → clarify → shape passes (commit 842bc59). This pass
**documents**; it does not fix. Targets: `src/` (the detector is meaningless against
`App.svelte` alone, which contains no CSS).

Contrast figures are computed from the oklch tokens via the canonical Ottosson
OKLCH→linear-sRGB→luminance transform (a small script), not a visual guess. The
browser could not round-trip oklch→rgb for an independent check (canvas `fillStyle`
rejects oklch; DOM `getComputedStyle` returns the oklch string unconverted), so the
transform is the source of truth here. The results are internally consistent and
on-scale (body text ~13:1, dim ~5:1), which is the sanity check that matters.

## Implementation Integrity Verdict

**Pass.** The implementation expresses a coherent, product-specific system, not an
interchangeable one. Verified evidence:

- **Two-ink/two-hand discipline is encoded, not hoped for.** The mono selector list
  (`app.css:162-176`) explicitly enumerates the machine's voice (labels, nav, buttons,
  inputs, eyebrow, meta, rule-label); the serif is bound to `.note-body`, `.note h2`,
  `textarea.dump`. A third face or a crossed wire would be visible in the stylesheet,
  and there is none.
- **State is the material.** Wet Ink (`--ember`) and Dry Ink (`--set`) are each
  referenced only where state is the meaning: ember on the pending eyebrow / countdown
  edge / active tab underline / primary commit; set on the filed line / links /
  citations / teal edge. No decorative use.
- **Detector:** one finding — the `.answer` 2px Dry Ink `border-left` (side-tab tell,
  `app.css:609`). This is the pre-existing AI-slop tell already catalogued and
  deliberately deferred to its own pass; it is not new drift.
- No hard-coded colors anywhere in `src/` (grep for hex/rgb/hsl literals returns none).
  `index.html` carries two hex `theme-color` values, which is correct — `theme-color`
  must be a concrete color and lives outside the token system by necessity.

Score 4: coherent and intentional. The single detector finding is tracked, not
systemic.

## Detailed Findings by Severity

### [P1] Primary button label below AA contrast in light mode
- **Location:** `app.css:277-282` (`button.primary`), token `--ember-light` / `--ground`
- **Category:** Accessibility (WCAG 1.4.3 Contrast (Minimum))
- **Impact:** The committing control — Capture, Ask, Save settings — the action the
  whole app exists to reach — has 4.16:1 contrast for its label in light mode. Normal
  text (mono 0.8125rem ≈ 13px, weight 500) requires 4.5:1. Low-vision users in the light
  scheme get a slightly hard-to-read label on the button they press most.
- **WCAG/Standard:** 1.4.3 Contrast (Minimum), AA. Fails by 0.34. Dark mode passes
  (7.68:1); the disabled primary (4.23:1) is exempt as an inactive component.
- **Recommendation:** Darken `--ember-light` lightness a step (58% → ~54%) so the
  Page-coloured label clears 4.5:1. This also lifts the eyebrow-on-card (currently 4.53,
  barely passing) further from the line, and does not affect the countdown edge or tab
  underline (non-text, 3:1, already fine). A pure-token change — every ember surface
  moves together, which is the point of the system.
- **Suggested command:** `/impeccable colorize`

### [P2] Post-save vault links are below the touch-target floor
- **Location:** `app.css:511-522` (`.vault-link`), `app.css:583-590` (`.note .links li`)
- **Category:** Responsive / Accessibility (WCAG 2.5.8 Target Size (Minimum), AA)
- **Impact:** The filed path, every Related link and every Ask citation are the doors the
  shape pass built — and on a phone they are ~13px-tall inline links with no vertical
  padding, stacked on a 0.25rem gap. A thumb lands two at once or misses. These are the
  peak-end payoff of the whole flow; they should be the easiest thing to hit, not the
  hardest.
- **WCAG/Standard:** 2.5.8 Target Size (Minimum), AA — 24×24px (the links sit well under
  that in height).
- **Recommendation:** Give `.vault-link` and `.note .links li` a min-height / padding so
  each link is a real touch target (the 44px floor is for commit controls, but a
  comfortable ≥32-40px here is the right call for a list of follow-through links). Keep
  the Dry Ink, no-underline-at-rest treatment.
- **Suggested command:** `/impeccable adapt`

### [P2] The Dump textarea has no accessible name
- **Location:** `App.svelte:519-526` (the `textarea.dump`)
- **Category:** Accessibility (WCAG 1.3.1 Info and Relationships / 4.1.2 Name, Role, Value)
- **Impact:** The field the user types their thought into is identified to assistive tech
  only by its `placeholder` ("What are you thinking?"). A placeholder is a hint, not a
  name; screen readers may announce it but it is not a stable accessible name and it
  vanishes on input. The "add context" field is correctly labelled (it is wrapped in a
  `<label>`); the Dump is not.
- **WCAG/Standard:** 1.3.1 / 4.1.2.
- **Recommendation:** Add an accessible name without changing the visual — a
  visually-hidden `<label>` bound to the textarea, or `aria-label="Capture a thought"`.
  Do not promote the placeholder into a visible label (the field is meant to read as a
  page, not a form field — see DESIGN.md "Don't let the capture field look like a form
  field").
- **Suggested command:** `/impeccable harden`

### [P2] Field/card borders fail the non-text 3:1 floor
- **Location:** `app.css:312-314` (`input,select,textarea` border), `app.css:418`
  (`.note` border); token `--rule`
- **Category:** Accessibility (WCAG 1.4.11 Non-text Contrast)
- **Impact:** `--rule` is ~1.32:1 (light) / ~1.40:1 (dark) against the ground, below the
  3:1 floor for the visual boundary of a UI component. The Note card is rescued by its
  two-layer shadow, so it still reads as lifted. Plain inputs are not — their fill
  (`--raised` 100% white) is only ~1.04:1 against the ground (97% off-white), so the
  near-invisible hairline is the only thing drawing the field's edge. A low-vision user
  in light mode may struggle to locate text fields.
- **WCAG/Standard:** 1.4.11 Non-text Contrast (3:1).
- **Recommendation:** This is a deliberate "hairline ruling" aesthetic, so it is a
  judgment call, not a bug. Two low-tradeoff options: (a) raise `--rule` chroma/lightness
  just enough to clear 3:1 while staying a hairline, or (b) widen the fill/ground gap
  (cooler or darker `--ground`, or a faintly tinted input fill) so the boundary reads
  without relying on the border. Decide in the colorize pass.
- **Suggested command:** `/impeccable colorize`

### [P3] No h1; heading hierarchy starts at h2
- **Location:** `App.svelte:500-507` (masthead wordmark is a `<span>`), `:552` (only
  heading is `<h2>`)
- **Category:** Accessibility (WCAG 1.3.1 Info and Relationships)
- **Impact:** The page has no `<h1>`. Screen-reader heading navigation begins at the
  note title (h2), skipping a document level. The wordmark "brain-dump" is the natural
  h1 but is a span.
- **Recommendation:** Make the wordmark an `<h1>` (visually unchanged — it keeps the
  mono/small/pencil treatment), or add a visually-hidden h1. Cheap.
- **Suggested command:** `/impeccable harden`

### [P3] Masthead `<header>` is inside `<main>`, so it is not a banner landmark
- **Location:** `App.svelte:499-507`
- **Category:** Accessibility (WCAG 1.3.1)
- **Impact:** A `<header>` only becomes a `banner` landmark when it is a direct child of
  `<body>`. Here it is inside `<main>`, so it has no landmark role; the page offers only
  `main` to landmark navigation.
- **Recommendation:** Either move the masthead outside `<main>` (structural), or add
  `role="banner"` to it. Minor.
- **Suggested command:** `/impeccable harden`

### [P3] View-switch tabs convey "current" only by colour, not by ARIA state
- **Location:** `App.svelte:502-506`
- **Category:** Accessibility (WCAG 1.3.1 / 4.1.2)
- **Impact:** The capture/ask/settings tabs toggle `class:on` (an ember underline +
  graphite text) but expose no `aria-current` / `aria-selected` / `aria-pressed`. A
  screen-reader user is told the state changed only by the status line, not by the
  control itself.
- **Recommendation:** Add `aria-current="page"` (or `aria-pressed`) to the active tab.
  One attribute per button.
- **Suggested command:** `/impeccable harden`

### [P3] Nav tabs and config checkbox are under the 24px touch floor
- **Location:** `app.css:217-228` (`nav button`, padding `0.25rem 0`), `App.svelte:669`
  (the case-sensitive checkbox label)
- **Category:** Responsive / Accessibility (WCAG 2.5.8)
- **Impact:** Nav tabs are ~21px tall — under the 24px AA minimum target. The config
  checkbox is a native ~16px control. Both are reachable but small for touch; the nav
  tabs are deliberately slim ("nav tabs are text, not commit buttons, and stay slim" —
  DESIGN.md), so this is a known tradeoff, not an oversight.
- **Recommendation:** Add a little vertical padding to the nav tabs to clear 24px
  without making them look like buttons (e.g. `padding: 0.5rem 0`). Leave the checkbox.
- **Suggested command:** `/impeccable adapt`

## Patterns & Systemic Issues

There is no systemic drift. The only cross-cutting pattern is a **tradeoff between the
notebook "hairline" aesthetic and the WCAG non-text 3:1 floor** — the rule borders and
the slim nav tabs both honour the material metaphor at the cost of contrast/target
size. These are deliberate, so the fix is a small calibration (a stronger rule, a touch
more padding), not a rethink. Everything else is isolated.

One non-issue worth recording so it is not re-flagged: `index.html`'s hex
`theme-color` values are *correct* outside the token system, not a theming lapse.

## Positive Findings

- **Theming is exemplary.** Zero hard-coded colors in `src/`; every color resolves
  through `light-dark()` with a `prefers-color-scheme` fallback; dark mode is fully
  designed, not an afterthought (the card shadow is re-cast per scheme — darker, wider,
  more present against the dark ground). This is the standard to maintain.
- **Motion is handled correctly.** `prefers-reduced-motion` kills the countdown
  animation and keeps the edge full, while *preserving* the wet→dry colour cross-fade
  because it carries state and is not vestibular — exactly the playbook's rule. No
  flashing, no layout-property animation, no `will-change` left on at rest, no
  unbounded blur/filter. The one authored motion (the commit) is a 2px line scaling in
  X — cheap and composited.
- **`index.html` sets `lang`, viewport, `color-scheme` and per-scheme `theme-color`
  before first paint**, so the canvas and scrollbars theme correctly with no flash.
- **Keyboard support is real**, not decorative: `:focus-visible` draws a 2px ember
  outline offset 2px, tab order is DOM-natural, and ⌘/Ctrl+Enter commits from every
  commit field.
- **Touch targets for committing controls** are held to 44px (`app.css:352-354`),
  border-box, shared across the row.
- **Status is the one feedback channel and it announces itself**: `aria-live="polite"`
  on status, the queue banner and the queue error.
- **No images, no icon fonts, no CDN** — the offline path is unbroken; fonts are
  self-hosted woff2.
